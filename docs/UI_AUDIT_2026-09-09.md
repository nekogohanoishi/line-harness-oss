# LINE Harness 管理画面 UI/UX 調査と改善案

調査日: 2026年9月9日

対象: 本番管理画面 `https://line-harness.nekogohanoishi.workers.dev/admin`

作業種別: 調査・改善案の作成のみ。ソースコード、本番設定、配信文面、DB、デプロイは変更していない。

## 1. 結論

問題の中心は、機能数ではなく「自分がやりたい操作を、正しい対象に対して、迷わず行えるか」にある。

特に不足しているのは次の5点。

1. **今動いている配信を一か所で把握すること。** 友だち追加、シナリオ、自動返信、共有テンプレート、予約メッセージが別画面に分かれ、全体のつながりが見えない。
2. **どの配信でも同じ方法で本文・ボタン・見た目を編集すること。** 自動返信ではフォーム編集できる一方、一斉配信のFlexはJSON入力が残る。
3. **状態を信用できること。** 配信なしを「停止中」、一斉配信の登録件数を「配信数（合計）」と表示するなど、名称と意味がずれている。
4. **日常の対応を少ない手順で進めること。** チャット、未対応一覧、友だち詳細、回答一覧を往復する必要がある。
5. **送信結果から改善につなげること。** データはあるが、解説速報受取から作成会希望までを、人数・割合・対象者で追える画面としてまとまっていない。

Lステップの画面を丸ごとコピーする必要はない。公式スクリーンショットにも細かい設定の密集は見られる。取り入れるべきなのは、共通エディター、検索条件の再利用、テスト導線、結果と対象者を行き来する仕組みである。

## 2. 調査方法と限界

- ログイン済みChromeで、サイドバーにある主要31ページを実際に開いて目視確認した。配信・テンプレート・リッチメニュー等は編集画面も確認した。
- 新規フォームの表示やキャンセルは行ったが、作成・保存・送信・停止・削除・公開操作は行っていない。
- 個別チャットの詳細確認には、既に確認済みのテスト用連絡先を使用した。顧客名、回答内容、認証情報は本書に転載していない。
- 友だち追加・ブロックの画面は、閲覧自体で確認状態が変わる実装であることに留意する。監査のための受信・配信設定変更は行っていない。
- 通常の表示領域は幅1132px・高さ644px。横幅不足の指摘は、この小さめのPC画面での観察であり、すべての解像度で同じ崩れがあるという意味ではない。
- スマホ幅390pxへの切替を試みたが、ツールの設定が実画面に反映されなかった。実寸を確認し、設定をリセットした。**スマホ実表示は未検証**。
- Lステップは公式の機能説明・操作手順・公開スクリーンショットとの比較。契約済みLステップ環境で全機能を操作した比較ではない。
- 一部の表示問題はローカルコードも読んで裏付けた。ただし、ローカルには未コミット変更があるため、コード上の指摘と本番で再現した事実は区別している。
- 空の機能で、リソースを作らないと進めない詳細画面は未検証。「見つけられない」と「実装されていない」を区別した。
- 本書は現状を新たに確認した記録。7月の既存競合調査書にある30秒同期などを、現在の仕様とみなしてはいけない。

## 4. 最優先で直すべき具体的な問題

### A. テンプレートから使用中シナリオへ進めない

テンプレート編集の「使用箇所」リンクが `/scenarios/detail?...` となり、必要な `/admin` が抜けている。実際にクリックすると管理画面の外へ遷移し、今回のChromeでは `ERR_BLOCKED_BY_CLIENT` が表示された。ブラウザのブロック理由までは断定しないが、生成リンクの誤りは確認できた。

改善: 管理画面用リンク生成に統一し、一覧ではなく使用中の該当ステップを開く。直接アクセス・再読み込みまで回帰確認する。

コード根拠: [templates/page.tsx:649](/Users/soom.l/Documents/02_Local_Dev/03_Variable/line-harness/apps/web/src/app/templates/page.tsx:649)。

### B. 「停止中」が配信停止を意味していない

友だち一覧では、表示対象シナリオが存在しない場合も「停止中」と出る。配信を止めた人、既に完了した人、まだ登録していない人を区別できない。個別の停止操作を信用できなくする表示である。

改善: 「予定なし」「配信待ち」「配信中」「一時停止」「完了」をデータに基づいて区別する。シナリオがないだけで、遅延自動返信もないとは判断しない。

コード根拠: [friend-list-row.tsx:156](/Users/soom.l/Documents/02_Local_Dev/03_Variable/line-harness/apps/web/src/components/friends/friend-list-row.tsx:156)。

### C. 「全配信停止」の名前と対象が一致しない

緊急コントロールの「全配信停止」は、説明とコード上ではスケジュール済み一斉配信を下書きに戻す操作。通常シナリオ停止は別ボタンで、遅延自動返信等をすべて停止する操作ではない。緊急時に「全部止まった」と誤認させる。

さらにローカルコードでは個別更新の `Promise.allSettled` の結果を判定せず、一覧取得が失敗応答でも完了状態へ進める。**本番で停止操作を実行して再現したわけではない**が、安全上、先に確認すべき実装上の問題。

改善: まず「予約済み一斉配信を取り消す」と対象を正確に表示。成功・失敗件数を読み戻す。真の全配信停止が必要なら、別途、全送信経路の送信直前チェックを備えた機能として実装する。ボタン名だけ変えて対応範囲を広げたことにしない。

コード根拠: [emergency/page.tsx:42](/Users/soom.l/Documents/02_Local_Dev/03_Variable/line-harness/apps/web/src/app/emergency/page.tsx:42)、[同ページ:79](/Users/soom.l/Documents/02_Local_Dev/03_Variable/line-harness/apps/web/src/app/emergency/page.tsx:79)。

### D. ダッシュボードの数字の意味が分からない

「配信数（合計）0」は、一斉配信レコード数を表示している。自動返信やシナリオを含む送信通数ではなく、下書き等も含み得る登録件数。名前から読み取れる意味と違う。

友だち数75と一覧79の差は、コード上、フォロー中のみの件数とブロックを含む一覧の違いで説明できる。複数アカウントが原因という推測はしない。

改善: 「一斉配信の登録件数」と正確に呼ぶか、目的に合う送信通数へ集計を変更。友だちは「フォロー中」「ブロック中」「登録合計」を分ける。各指標のクリック先にも同じ条件を渡す。

コード根拠: [app/page.tsx:197](/Users/soom.l/Documents/02_Local_Dev/03_Variable/line-harness/apps/web/src/app/page.tsx:197)、[friends.ts:399](/Users/soom.l/Documents/02_Local_Dev/03_Variable/line-harness/apps/worker/src/routes/friends.ts:399)。

## 6. 目指す画面構成

### A. ホーム

大きなカードを並べるのではなく、上から次を置く。

1. 最終更新時刻と手動更新。
2. 未確認・要対応・今日の配信・送信失敗の件数をコンパクトに表示。
3. 「返信が必要な相手」と「これから送られるメッセージ」の一覧。
4. 受取数・案内数・申込数の期間別集計。

予約は、現行運用で使う場合だけ上位に出す。Googleフォームからの受付を、Harness内予約と勝手に同一化しない。

### B. 現在有効な配信

基本表示は、自由配置の複雑なフローチャートではなく、読み順のある時系列リストにする。

```text
友だち追加・ブロック解除
  あいさつ → 解説速報の受取ボタン

「解説速報を受け取る」への反応
  直後: 閲覧案内
  当日または翌日20:00: 作成会案内
  18:00まで／以降の判定を表示

「作成会希望」への反応
  指定済みの自動返信

「入力完了」への反応
  指定済みの自動返信
```

これは一覧表示案であり、配信設定の変更指示ではない。実装時には改めて本番の条件・除外・送信経路を読み戻して構築する。

各行に「有効状態・対象・本文プレビュー・編集元・次の処理」を置く。変更は該当する既存設定に反映し、表示用に同じ配信設定を二重保存しない。

### C. 共通のメッセージ編集画面

- 上部: 配信名、どこで使われているか、保存状態。
- 中央: 本文とブロック編集。十分な横幅があるときだけ右にLINEプレビュー。
- 狭い画面: 編集／プレビューを切り替え、細い2列を作らない。
- 下部: 保存、テスト送信、キャンセル。同じ位置に固定。
- 詳細: データキー、JSON、内部ID等は折りたたむ。

見た目は白地・区切り線・控えめな色を基本にし、ページ全体や編集欄を何重にもカードで囲まない。色は状態を補助するために使い、色だけで有効・無効を伝えない。

参考として、Lステップの[公式編集画面](https://linestep.jp/wp-content/uploads/2024/09/flex72.png)、[個別トーク画面](https://linestep.jp/wp-content/uploads/2023/05/kobetu7.png)、[詳細検索画面](https://linestep.jp/wp-content/uploads/2023/09/custom2-e1695780211186.jpg)も実際に目視した。表層の色や装飾ではなく、編集領域の取り方と操作のまとまりを参考にする。

## 7. 推奨する実装順

### 第1段階: 誤解と操作不能をなくす

対象: No.09・31・41・57、主要画面のはみ出し。

- 間違ったリンク、停止状態、件数ラベル、緊急操作結果を修正。
- 本番の配信設定を変更せず、表示と安全性を直す。
- 完了基準: テンプレート使用箇所から正常に移動できる。予定なしの人を停止中と出さない。全停止の対象が名称と一致する。ダッシュボードと一覧の集計条件が一致する。

### 第2段階: 有効な配信を見つけ、本文を直せるようにする

対象: No.19〜27・31〜38・58。

- 「現在有効な配信」と共通メッセージ編集を作る。
- まず既存の自動返信とテンプレート1件で工程を固め、その後シナリオ・一斉配信へ展開する。
- 完了基準: 20時配信の本文に一覧から2操作以内で到達。JSONを触らず変更できる。共有元の変更対象が分かる。保存・プレビュー・テストが同じ場所にある。

### 第3段階: チャットと対象管理を整える

対象: No.10〜18・48。

- 対応待ちをチャットへ統合し、保存検索と友だち情報パネルを追加。
- 現行の配信停止・再開機能を活かし、送信待ちの内容と予定時刻を見せる。
- 完了基準: 受講生を検索し、その人だけの今後の配信を確認・停止できる。未確認と未対応の意味を混同しない。

### 第4段階: 申込率と回答結果を見えるようにする

対象: No.42〜47・49・60。

- 今の申込方法を変えず、保存済みイベント・メッセージ・フォーム記録から取得できる範囲を整理。
- 完了基準: 分母・期間・重複除外を指定して申込率が見える。グラフの人数から該当者へ移動できる。取得できない段階は未計測と表示する。

### 第5段階: 低頻度画面・レスポンシブの仕上げ

対象: 予約・外部連携・複数アカウント管理・全体品質。

- 高度な機能を消すのではなく、通常運用から整理して分ける。
- 完了基準: 小さめPCとスマホで名前・状態・主要操作が切れない。権限別に不要な危険操作を見せない。手動更新時以外の大量再取得を発生させない。

具体的な工数は、共通エディターと予約メッセージの取得APIを確認してから見積もる。画面の名称変更と、送信経路の統合制御を同じ規模の作業とは扱わない。

## 8. 残すべき現行の改善

- アンケートの「選択中・停止」「無効」の明示。
- 自動返信の複数メッセージ編集と、18時締切・20時送信の日本語表示。
- チャットに追加した「配信の停止・再開」と、停止中に時刻を過ぎた予約メッセージを後から送らない説明。
- シナリオの一括プレビュー、ステップ別テスト送信、テスト受信者設定。
- テンプレートの利用数、使用箇所、共有変更の影響に関する注意表示。
- リッチメニューのLINE側との差分確認、下書き保存とLINEへの反映の分離。
- 友だちのブロック状態・日時、追加・ブロック・解除の履歴一覧。
- 手動更新方針。新しい通知機能のために常時ポーリングを戻さない。

## 9. 変更してはいけない運用

- メッセージ本文、キーワード、ボタン文言、送信時刻をUI改善と一緒に無断変更しない。
- 無効のアンケートを再開しない。
- 受取から作成会への流れを変更しない。
- サイト内予約や空き日程リンクを勝手に導入・再開しない。
- 1アカウント運用の問題を、複数アカウントのせいと推測しない。
- 送信成功、既読、リンク閲覧、フォーム入力、申込は別の事実。取得できない既読・閲覧を推定の確定値で表示しない。
- 友だちの受信内容や回答を、外部サービスの検証データとして無断送信しない。
